# 系统升级控制台设计

状态：方案已确认，尚未实施。本文是实施基线，不代表当前生产环境已经具备页面升级或自动回滚能力。

## 1. 目标与边界

- 管理员可上传经 CI 构建和验证的主应用 JAR，查看发布进度与历史，并在控制台发起发布。
- 发布可执行主应用 JAR 切换和该 JAR 内的 Flyway 数据库迁移。
- 主应用停机或新版本启动失败时，升级控制台和进度页面仍可用。
- 发布验证阶段失败时，自动恢复旧 JAR、应用数据库和导入源文件；验证通过并恢复写入后，只允许受控的人工恢复流程，并明确可能丢失的写入。
- 首期针对现有单机、单实例生产部署。主机整体故障、多节点编排和升级控制台自我升级不在首期范围。

这里的“独立子模块”指独立构建、独立进程、独立页面资源和独立持久状态。仅把代码放进另一个 Maven 目录、最终仍打进主 JAR，不能满足主应用停机时可操作的要求。

## 2. 仓库现状与设计依据

- 根目录 `pom.xml` 当前构建一个可执行 JAR，Vue 静态资源被打入该 JAR；Nginx 模板把页面请求代理给主应用。
- 生产未使用 Jenkins，目前生产 JAR 在本地打包。现有 `.github/workflows/verify.yml` 会测试和打包，却尚未归档可供上传核验的正式 JAR；已决定扩展它作为唯一的正式产物构建来源。生产使用的 [daemon.sh](../../deploy/daemon.sh) 只负责主应用启停，不负责 JAR 替换或备份；当前手工替换动作仍待核对。
- 主应用使用内存会话，重启后会话失效；升级控制台不能复用 `IR_SESSION` 作为授权依据。
- 根作用域 Service Worker 会处理同源页面请求。升级控制台使用独立 HTTPS 站点，由主后台菜单打开，避免主应用停机及缓存策略影响控制台。
- 当前构建产物约 62 MB，而现有 Nginx 模板的上传上限为 10 MB。仅为升级站点配置有界、可调整的上传上限，不扩大普通业务上传限制。
- 已归档的[生产脚本](../../deploy/daemon.sh)以 `ireader` 用户运行，JAR 固定为脚本所在目录的 `interview-reader.jar`，默认文件存储目录为同目录的 `data`，使用 `nohup`、PID 文件和 `flock` 管理进程。它拒绝符号链接 JAR，启动后 2 秒只检查进程存活，停止超过 30 秒会发送 `SIGKILL`。这些行为与版本切换、就绪验证和安全排空必须分别衔接。
- 用户提供的目录截图显示 `data` 根目录下有哈希命名目录，同时有 `data/import-sources/` 下的哈希目录和 `data/target/pdfbox-font-cache/`。代码中的 `SourceFileStorage` 在实际配置的 `INTERVIEW_READER_STORAGE_DIR` 根下按哈希保存文件；用户已确认生产 `INTERVIEW_READER_STORAGE_DIR=/opt/ireader/data`。数据库保存的是相对对象键，读取时会拼到当前配置的存储根；如果曾变更存储根却未迁移文件，旧文件可能无法读取。无法仅凭截图认定两批文件的来源或使用情况。主进程工作目录是 `data`，因此 PDFBox 在该目录下创建的 `target/pdfbox-font-cache` 属于可重新生成的字体缓存。
- MySQL 迁移位于主 JAR 内，由 Flyway 在新版本启动时执行。仓库没有通用的反向迁移脚本；现行[运行手册](../operations/runbook.md)要求迁移失败时从同一批次的数据库与源文件备份恢复。
- 导入和永久删除 Worker 在主进程执行，永久删除任务还会在启动后恢复执行。因此，仅在 Nginx 拦截写请求不足以保证验证阶段没有后台写入。

## 3. 组件与责任

| 组件 | 责任 |
|---|---|
| GitHub Actions | 扩展现有验证工作流，在主分支成功构建后归档唯一正式 JAR、不可变运行 ID、Git 提交和服务端 SHA-256；本地打包产物不再作为可发布来源。 |
| 升级控制台 | 提供独立页面、认证、上传暂存、产物核验、操作状态和审计；主应用或主数据库不可用时仍能展示本地持久状态。 |
| 受限部署执行器 | 串行执行维护、备份、进程切换、检查和恢复；以 `ireader` 身份调用现有 `daemon.sh` 的固定命令；只能处理服务端生成的发布 ID，不能接受任意命令、路径或脚本。 |
| 主应用 | 提供可跨重启保持的维护门禁与任务排空状态；维护期间不接收新写入，也不自动恢复后台写任务。新版本仍由自身 Flyway 完成迁移。 |
| Nginx 与进程管理 | Nginx 分别代理主站和升级站点；主应用沿用现有 `daemon.sh`，控制台由独立进程管理器托管。除非另做迁移，不给主 JVM 同时叠加 systemd 生命周期管理。 |

为减少对现有根 `pom.xml` 的改造，升级服务可以先作为仓库中的独立构建项目，而非把根项目立即改成 Maven 聚合工程。它不依赖主应用的运行时类或主数据库表。控制台页面由升级服务自身或它的专用 Nginx 静态目录提供。

现有 `daemon.sh` 的 `flock` 只保护一次启停命令；升级服务仍需持有覆盖上传后发布、备份、切换和恢复全过程的独占操作锁。现有脚本由 `ireader` 用户读取 root 所有的 `application.env`，因此环境文件还必须授予该用户只读权限（例如受限组或 ACL）；单纯 root `0600` 无法被此脚本读取。

## 4. 产物与权限契约

1. 上传请求必须带 GitHub Actions 的不可变运行 ID。服务端计算 JAR 的 SHA-256，通过受认证的只读通道从对应主分支成功运行的归档记录核对摘要、提交和测试结果。浏览器上传的哈希或清单不能单独证明产物来自 CI；本地打包 JAR 不可发布。
2. 上传采用流式写入到控制台私有暂存目录，限制大小、数量和磁盘占用；完成校验后才以原子重命名标记为可发布。拒绝重复构建、损坏 JAR、非可执行 JAR 和目标环境不匹配的产物。
3. 控制台使用独立管理员认证，限制在内网或 VPN，经 HTTPS 暴露；写接口实行服务端授权、Origin/CSRF 校验和审计。主应用的 Cookie 不授予升级权限。
4. Web 服务账号不能直接获得 root、数据库超级用户或任意系统命令执行权限。部署执行器仅允许预定义动作，配置和备份凭据由受保护的环境文件提供，日志不得包含密钥。
5. 单机只允许一个升级或恢复操作运行。升级服务将操作状态和必要日志持久化在自己的数据目录，不依赖主应用数据库。控制台重启后必须能识别未完成操作；状态不明时保持维护门禁并要求人工核实，不能猜测成功。

## 5. 发布状态与顺序

建议的操作状态：

`STAGED → PRECHECKING → DRAINING → STOPPING → BACKING_UP → SWITCHING → STARTING → VERIFYING → SUCCEEDED`

在备份之前失败，记录 `FAILED`；若主进程已停止，须先验证旧版重新就绪，再解除维护门禁。在切换或验证阶段失败，进入 `ROLLING_BACK → ROLLED_BACK`。恢复失败或状态无法判定时进入 `NEEDS_OPERATOR`，保持主站写入关闭。

具体顺序：

1. **预检**：确认产物身份、Java 版本、磁盘容量、数据库和备份目标可用；在与生产版本同构的 MySQL 副本上完成迁移和回归验证。任一预检失败则不动生产。
2. **关闭入口并排空任务**：Nginx 将主站切到维护响应；主应用维护门禁阻止新写入、导入和删除任务，等待已运行任务结束。超过配置时限则取消升级并恢复原服务，不强行截断任务制作备份。
3. **停止与备份**：任务排空后，以 `ireader` 身份调用 `daemon.sh stop` 并确认主进程退出；升级路径必须先改造现有 30 秒超时后 `SIGKILL` 的行为，优雅停止超时应中止切换并保留维护状态，不能强杀后继续备份。随后保存旧 JAR、所需配置、应用数据库和完整的 `<APP_DIR>/data`；若 `INTERVIEW_READER_STORAGE_DIR` 指向该目录之外，还须一并保存那个目录。首期不只备份 `data/import-sources`，避免遗漏截图中 `data` 根下的文件；待核实数据库对象键与实际配置后，再决定是否排除可重建的字体缓存。所有数据使用同一备份批次号并校验备份。备份失败则重启旧版并解除维护。
4. **切换与迁移**：在与运行 JAR 相同的文件系统暂存版本文件，再原子替换脚本固定读取的 `interview-reader.jar`；不可用符号链接切换，因为当前脚本会拒绝。以 `ireader` 身份调用 `daemon.sh start`，再独立等待就绪；脚本的 2 秒进程存活检查不能代表发布成功。新 JAR 的 Flyway 在启动时迁移数据库，跨重启维护标记让后台任务继续暂停。
5. **验证与开放**：检查进程、`/actuator/health/readiness`、主页静态资源和目标版本标识；确认通过后解除主应用维护门禁，恢复后台任务和外部流量，记录发布成功及备份 ID。数据库大小决定备份和恢复耗时，首期不承诺秒级停机。

维护门禁是主应用需要新增的能力：升级服务在部署目录之外原子写入受保护的维护标记；主应用启动时读取它，通过仅本机可用且经过认证的控制接口报告任务排空状态，并在标记解除后恢复后台任务。门禁须覆盖写接口与后台任务，并在主应用重启后继续生效。当前永久删除 Worker 在 `ApplicationReadyEvent` 后恢复任务；若不改造，验证阶段可能发生写入。门禁解除前不能把新版本视为已发布成功。

## 6. 回滚与恢复

- **验证阶段自动回滚**：新版本启动、Flyway 或就绪检查失败时，停止新进程，恢复同一备份批次的应用数据库与源文件，切回旧 JAR 和必要配置，启动旧版并验证就绪。恢复成功后解除维护门禁并标记 `ROLLED_BACK`。
- **发布成功后的人工恢复**：控制台展示备份时间和预计丢失写入的时间窗。操作员明确选择备份并再次确认后，重新关闭写入、排空任务，先保存当前状态，再恢复选定备份与匹配的旧 JAR。此流程不宣称无损。
- **恢复失败**：控制台保持在线，保留维护门禁、日志、各备份和产物；标记 `NEEDS_OPERATOR`。不能自动开放一个数据库与 JAR 版本不匹配的主站，也不能删除 Flyway 历史行伪造回滚。
- 备份策略和恢复演练沿用并扩展[生产运行手册](../operations/runbook.md)。数据库和源文件必须作为同一恢复点处理。

## 7. 最小页面与 API

主后台菜单只增加“系统升级”入口，跳转专用站点。该站点提供当前版本、上传与校验结果、单次发布进度、历史记录、恢复入口和可下载的脱敏日志。页面状态从升级服务获取，不依赖主应用 API。

独立 API 的最小资源可定义为：

| 方法与路径 | 用途 |
|---|---|
| `POST /api/releases` | 上传 JAR 和 GitHub Actions 运行 ID；返回暂存发布 ID、校验结果。 |
| `GET /api/releases`、`GET /api/releases/{id}` | 查询可用产物与当前/历史发布详情。 |
| `POST /api/releases/{id}/deployments` | 以幂等键创建一次发布操作；已有运行中操作时拒绝。 |
| `GET /api/operations/{id}` | 查询状态、阶段、时间和可操作的错误摘要；页面轮询即可。 |
| `GET /api/operations/{id}/events` | 分页查看脱敏操作事件。 |
| `POST /api/recoveries` | 发起人工恢复；请求包含备份 ID 与明确的数据丢失确认。 |

控制台维护自己的 OpenAPI 契约，不把这些接口混入主应用现有 `docs/api/openapi.yaml`。所有发布和恢复请求都必须由服务端再次验证状态与权限，不能依赖前端按钮禁用。

## 8. 实施顺序与验收

1. **校准现网**：用户已确认提供的 `daemon.sh` 正在生产使用，且存储根为 `/opt/ireader/data`。继续核对脚本安装目录、实际 JAR 替换动作、环境文件权限、Nginx 配置、数据库规模与备份时长；以当前存储根与数据库相对对象键核对文件，并调查 `data/import-sources` 中文件的来源。生产当前由本地打包，须核对手工替换 JAR 的步骤；正式发布将改用 GitHub Actions 产物。
2. **改构建与主应用**：扩展 `.github/workflows/verify.yml`，只为通过全部检查的主分支运行归档正式 JAR、SHA-256 与提交信息，提供升级服务可认证查询的记录；加入跨重启维护门禁和任务排空能力，并确保升级服务成为唯一生产发布入口。
3. **建独立控制台**：先实现上传核验、只读状态和独立认证，再实现单机串行发布与自动恢复；最后接入主后台菜单。
4. **隔离环境演练**：至少验证正常升级、假产物、备份失败、任务排空超时、Flyway 失败、新版就绪超时、控制台重启中断、自动回滚、人工恢复及恢复失败的保守状态。使用生产同类 MySQL 和数据副本，不连接未知数据库。
5. **更新运维手册后上线**：给出升级站点和凭据管理、目录权限、备份保留、人工接管和恢复演练步骤。验收以“主 JAR 停止期间页面可用且能看到持久进度”为必测项。

本设计不要求额外的配置中心、消息队列或多节点协调服务；单机串行操作和控制台本地持久记录足够覆盖首期目标。
